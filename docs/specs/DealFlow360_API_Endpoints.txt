DealFlow360 — API ENDPOINT SPECIFICATION
=============================================

DOCUMENT STATUS
---------------
Status: Proposed API Contract / Frontend-Backend Integration Reference
Purpose:
- Source-of-truth API contract for DealFlow360 implementation.
- Defines REST endpoints required to satisfy the finalized functional requirements.
- Intended for AI-assisted backend implementation, frontend implementation,
  API client/hook generation, testing, and integration work.
- Intended to be attached as a project source and treated as an implementation
  reference alongside the finalized Requirements & Scope and Database Schema.

AUTHENTICATION PRINCIPLE
------------------------
- Supabase Auth owns authentication credentials and authentication flows.
- FastAPI owns application-level authorization and business rules.
- FastAPI must validate the authenticated user's Supabase JWT.
- users table stores application-specific identity, role, and customer association.
- Do not implement a second independent password/authentication system in FastAPI.
- Customer portal APIs must enforce customer ownership/restriction server-side.

BUSINESS-LOGIC PRINCIPLE
------------------------
FastAPI is authoritative for:
- Pricing resolution
- Discount governance
- Discount risk calculation
- Blended risk score
- Approval requirement
- Approval routing
- Approval state transitions
- Margin calculation
- Upsell/cross-sell eligibility and ranking
- Warehouse allocation
- Backorder handling
- Subscription proration
- Subscription modification/cancellation behavior
- Refund/credit-note behavior
- Billing schedule generation
- Invoice status calculation
- Negotiation re-approval
- Deal health calculations
- Anomaly detection
- Delivery slippage detection
- Audit-log generation

Frontend validation may improve UX but must never be the sole enforcement
mechanism for business rules.

API DESIGN PRINCIPLES
---------------------
1. Use normal CRUD endpoints for configuration/read-heavy resources.
2. Use explicit action endpoints for business operations/state transitions.
3. Do not expose generic CRUD operations that allow the frontend to bypass
   business rules.
4. Business operations must validate current state before performing changes.
5. Business operations that change commercial terms must recalculate all
   affected pricing, margin, risk, and approval state.
6. Realtime UI updates should use Supabase Realtime where appropriate rather
   than unnecessary polling endpoints.
7. Reporting is query/aggregation based; no reports database table is required.
8. Audit logs are generated by backend business operations; frontend should
   not create arbitrary audit records.
9. Exact formulas not specified by requirements remain backend implementation
   decisions:
   - blended risk score
   - warehouse optimization
   - anomaly detection
   - delivery slippage
   - subscription proration

11. QUOTATIONS
======================================================================

GET /api/v1/quotations
Purpose:
- List quotations.
- Support filters:
  - status
  - customer
  - sales representative
  - date range
- Used by quotation list and sales workspace.

POST /api/v1/quotations
Purpose:
- Create a new quotation for a customer.
- Associate responsible Sales Representative.
- Initialize draft commercial state.

GET /api/v1/quotations/{id}
Purpose:
- Return complete quotation details.
- Include customer, sales rep, lines, totals, margin, risk, approval state,
  and relevant workflow information.

PATCH /api/v1/quotations/{id}
Purpose:
- Update allowed quotation metadata.
- Must enforce quotation lifecycle/state rules.
- Must generate audit records for important edits.

DELETE /api/v1/quotations/{id}
Purpose:
- Delete/deactivate quotation where allowed.
- Intended primarily for drafts.
- Must reject deletion when business state does not permit it.

GET /api/v1/quotations/{id}/lines
Purpose:
- Return quotation lines.

POST /api/v1/quotations/{id}/lines
Purpose:
- Add product/variant to quotation.
- Resolve authoritative pricing.
- Calculate initial line values.
- Recalculate quotation totals, margin, risk, and approval requirement.

PATCH /api/v1/quotations/{id}/lines/{line_id}
Purpose:
- Change quotation line quantity, variant, or line-level discount.
- Recalculate affected pricing, totals, margin, risk, and approval state.
- Capture relevant snapshots for auditability.

DELETE /api/v1/quotations/{id}/lines/{line_id}
Purpose:
- Remove quotation line where quotation state permits.
- Recalculate totals, margin, risk, and approval state.

POST /api/v1/quotations/{id}/recalculate
Purpose:
- Recalculate the quotation using current authoritative configuration/data.
- Recalculate:
  - prices
  - line totals
  - subtotal
  - discounts
  - tax
  - total
  - cost
  - margin
  - allowed discounts
  - discount excess
  - blended risk score
  - approval_required
  - current approval level
- Used after relevant quotation changes and frontend "reload/recalculate"
  operations.

GET /api/v1/quotations/{id}/risk
Purpose:
- Return current quotation risk state.
- Return blended risk score.
- Return approval requirement.
- Return required approval level.
- Return line-level discount limits/excess information for UI explanation.

POST /api/v1/quotations/{id}/submit
Purpose:
- Submit quotation into the next workflow state.
- Must recalculate first.
- Must automatically determine whether approval is required.
- If approval required:
  - create approval_instance
  - create required approval_steps
  - set quotation to PENDING_APPROVAL
- If approval is not required:
  - skip approval
  - make quotation eligible for confirmation/fulfillment according to
    lifecycle rules.
- Sales Rep must not manually decide/request approval.

POST /api/v1/quotations/{id}/send
Purpose:
- Mark quotation as sent to customer.
- Set sent_at.
- Set customer-visible status appropriately.
- Must enforce valid quotation state.

POST /api/v1/quotations/{id}/return-for-revision
Purpose:
- Return quotation to revision state where authorized.
- Intended for workflow actions requiring revision.

POST /api/v1/quotations/{id}/confirm
Purpose:
- Confirm quotation and create the corresponding order.
- Must verify:
  - quotation is in a confirmable state
  - required approval has completed
  - current terms are valid
  - authorization is valid
- Must create at most one order for the quotation.
- Must update quotation status to CONFIRMED.
- Must create required audit entries.

GET /api/v1/quotations/{id}/order
Purpose:
- Return order generated from the quotation.

GET /api/v1/quotations/{id}/approvals
Purpose:
- Return approval history and current approval workflow for quotation.

GET /api/v1/quotations/{id}/audit-log
Purpose:
- Return quotation-specific audit history.

15. APPROVAL EXECUTION
======================================================================

GET /api/v1/approvals
Purpose:
- List approval workflows visible to the authenticated user.
- Support status/role/quotation filtering where useful.

GET /api/v1/approvals/pending
Purpose:
- Return pending approval work relevant to current user.
- Must return only approval steps the current user is authorized to act on.

GET /api/v1/approvals/{id}
Purpose:
- Return approval instance including:
  - risk score
  - overall status
  - approval steps
  - current step
  - reviewer/role information
  - decision reasons
  - timestamps

POST /api/v1/approvals/{id}/approve
Purpose:
- Approve the current approval step.
- Validate current user's authorization.
- Validate step is pending and actionable.
- Record decision reason.
- Update approval step.
- If next sequential step exists, activate it.
- If final step is approved, complete approval instance and update quotation.

POST /api/v1/approvals/{id}/reject
Purpose:
- Reject the current approval step/workflow.
- Record reason.
- Update approval state and quotation state appropriately.
- Generate audit log.

POST /api/v1/approvals/{id}/return-for-revision
Purpose:
- Return quotation/workflow for revision.
- Record reason.
- Update approval state.
- Update quotation to REVISION_REQUIRED as appropriate.
- Generate audit log.

GET /api/v1/approvals/{id}/audit-log
Purpose:
- Return audit history related to approval workflow.

Approval invariants:
- Manager must precede Finance when Finance is required.
- Finance must not be shown/activated when policy does not require Finance.
- Approval actions must be sequential.
- Approval actions must be auditable.
- A quotation can have multiple approval_instances over its lifecycle.

Purpose:
- List payments.
- Support invoice/order/date/status filtering.

GET /api/v1/payments/{id}
Purpose:
- Return payment details.

POST /api/v1/invoices/{id}/payments
Purpose:
- Record a payment against invoice.
- Validate payment amount.
- Update invoice.paid_amount.
- Recalculate invoice status.
- Required status behavior:
  paid_amount = 0 after issuance -> ISSUED
  0 < paid_amount < total_amount -> PARTIALLY_PAID
  paid_amount >= total_amount -> PAID
- Must not logically allow overpayment unless future implementation explicitly
  supports it.

Purpose:
- Refund a recorded payment when supported.

28. CUSTOMER NEGOTIATION

Purpose:

Purpose:
- Submit customer negotiation/change request.
- Support:
  - requested discount
  - requested changes
  - reason
- On commercial changes, backend must:
  1. apply/record requested changes according to workflow design
  2. recalculate pricing
  3. recalculate margin
  4. recalculate discount risk
  5. determine approval requirement
  6. create new approval_instance if required
  7. update quotation status appropriately
- Must not allow customer to directly mutate authoritative quotation fields
  outside permitted negotiation behavior.

Purpose:
- Add customer line-level comment/question.
- Must validate that line belongs to quotation.

POST /api/v1/portal/quotations/{id}/confirm
Purpose:
- Customer confirms final quotation with one action.
- Must verify quotation is in customer-confirmable state.
- Must re-evaluate current commercial terms before confirmation.
- If final terms require approval:
  - do not bypass approval
  - create/re-enter approval workflow
- If no approval required:
  - confirm quotation
  - create order
  - continue toward fulfillment/billing.

29. NEGOTIATION RE-APPROVAL
======================================================================

No separate mandatory "reapproval" endpoint is required.

Primary trigger:
POST /api/v1/portal/quotations/{id}/negotiations

Secondary confirmation trigger:
POST /api/v1/portal/quotations/{id}/confirm

Required backend behavior:
- Any negotiation affecting commercial terms must recalculate risk.
- If threshold exceeded:
  - create a new approval_instance
  - create required approval_steps
  - set quotation to PENDING_APPROVAL
- If threshold not exceeded:
  - allow workflow to continue toward confirmation/fulfillment.
- Existing approval history must remain intact.
- Multiple approval_instances are valid for one quotation lifecycle.

======================================================================

Treat this document as the API integration contract unless a later explicit
project decision changes it.

When implementing or modifying an endpoint:
1. Preserve the finalized database schema.
2. Preserve the finalized functional requirements.
3. Preserve backend-authoritative business logic.
4. Preserve role-based authorization.
5. Preserve customer portal isolation.
6. Preserve automatic approval routing.
