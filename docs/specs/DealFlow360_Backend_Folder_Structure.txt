DealFlow360 — FINAL BACKEND FOLDER STRUCTURE
================================================

STATUS
------
Recommended implementation structure for the finalized DealFlow360 backend.

DESIGN BASIS
------------
This structure is derived from the finalized:
- Technology Stack
- Requirements & Scope
- Database Schema
- API Endpoint Specification

Confirmed backend architecture:
- Python
- FastAPI
- Pydantic
- SQLAlchemy 2.x
- Alembic
- PostgreSQL (direct/self-managed)
- FastAPI-owned manual authentication
- Realtime not required for core implementation
- Pytest
- Modular Monolith

PRIMARY ARCHITECTURAL RULE
--------------------------
The backend is the authoritative application/business-logic layer.

Keep these responsibilities separate:
1. Router/API layer:
   HTTP concerns, authentication dependencies, request/response handling.
2. Schema layer:
   Pydantic request/response validation and serialization.
3. Service layer:
   Business workflows and state transitions.
4. Engine layer:
   Complex reusable business calculations/rules.
5. Repository layer:
   Database queries and persistence operations.
6. Model layer:
   SQLAlchemy database mappings.
7. Core layer:
   Cross-cutting infrastructure such as DB session, configuration,
   authentication/JWT verification, authorization, exceptions, logging.

Do NOT put core business rules directly inside FastAPI route handlers.

2. app/main.py
======================================================================

Purpose:
FastAPI application entry point.

Contains:
- FastAPI app creation.
- Application startup/shutdown configuration.
- API router registration.
- Global exception-handler registration.
- Health-check endpoint if desired.
- CORS configuration.

- Discount calculations.
- Approval routing.

3. app/core/
======================================================================

Cross-cutting backend infrastructure used by all modules.

----------------------------------------------------------------------
core/config.py
----------------------------------------------------------------------
Purpose:
Central application configuration.

Contains:
- Environment variable loading.
- Authentication/JWT/cookie configuration.
- Database URL.
- JWT, refresh-session, cookie, and CORS-related configuration.
- CORS settings.
- Application environment.
- Other non-business configuration.

Business rules must NOT be stored here.

----------------------------------------------------------------------
core/database.py
----------------------------------------------------------------------
Purpose:
SQLAlchemy database infrastructure.

Contains:
- SQLAlchemy engine.
- Session factory.
- Base/declarative configuration.
- FastAPI database-session dependency.
- Transaction/session helpers where required.

Uses:
- PostgreSQL (direct/self-managed) through SQLAlchemy.

----------------------------------------------------------------------
core/security.py
----------------------------------------------------------------------
Purpose:
Authentication verification utilities.

Contains:
- Argon2id password hashing/verification helpers.
- Access JWT creation and validation.
- Refresh-token generation/validation helpers.
- Authenticated user extraction.
- Token/cookie security helpers.

Important:
FastAPI owns authentication credentials and authentication flows.
`auth_sessions` provides persistent refresh-session state.

Never store plaintext passwords or raw refresh tokens.

----------------------------------------------------------------------
core/dependencies.py
----------------------------------------------------------------------
Purpose:
Reusable FastAPI dependencies.

Contains:
- get_db()
- get_current_user()
- role-based authorization dependencies.
- Customer portal authorization dependency.
- Common resource-access checks where appropriate.

Example concepts:
- require_roles(...)
- require_internal_user
- require_customer_portal_user
- require_admin
- require_sales_manager
- require_finance_operations

Authorization must be enforced server-side.

----------------------------------------------------------------------
core/exceptions.py
----------------------------------------------------------------------
Purpose:
Application-specific exception classes.

Examples:
- ResourceNotFoundError
- UnauthorizedError
- ForbiddenError
- InvalidStateTransitionError
- BusinessRuleViolationError
- InsufficientInventoryError
- ApprovalRequiredError
- BillingError

----------------------------------------------------------------------
core/exception_handlers.py
----------------------------------------------------------------------
Purpose:
Convert application exceptions into consistent FastAPI HTTP responses.

Contains:
- Exception-to-status-code mapping.
- Consistent error response formatting.

----------------------------------------------------------------------
core/logging.py
----------------------------------------------------------------------
Purpose:
Application logging configuration.

Contains:
- Logging setup.
- Structured/request logging helpers if used.
- Error logging configuration.

======================================================================
6. app/modules/
======================================================================

This is the main business/application layer.

Each module should normally contain:

module/
├── __init__.py
├── router.py
├── schemas.py
├── service.py
└── repository.py

Where a module has unusually complex calculations, add:

├── engine.py

Where a module needs multiple services/repositories, split them into
additional files only when complexity justifies it.

Do not create dozens of tiny files before they are needed.

28. REQUEST FLOW
======================================================================

Recommended request flow:

HTTP Request
    |
    v
FastAPI Router
    |
    v
Authentication / Authorization Dependency
    |
    v
Pydantic Request Schema
    |
    v
Service
    |
    +------> Domain Engine
    |
    +------> Repository
    |            |
    |            v
    |        SQLAlchemy Models
    |            |
    |            v
    |        PostgreSQL
    |
    +------> Audit Service
    |
    v
Pydantic Response Schema
    |
    v
HTTP Response

For business operations, the service layer coordinates the transaction.

Example:
POST /quotations/{id}/submit
    -> auth dependency
    -> quotation service
    -> recalculate pricing/margin/risk
    -> discount engine
    -> approval policy selection
    -> approval service
    -> create approval_instance
    -> create approval_steps
    -> audit service
    -> commit transaction
    -> response

======================================================================
29. TRANSACTION BOUNDARY RULE
======================================================================

Business operations that modify multiple related records should execute as
one database transaction whenever consistency requires it.

Examples:

Quotation line update:
- update quotation line
- recalculate quotation
- update quotation totals/risk/margin
- audit change
- commit

Approval:
- update approval step
- update approval instance
- update quotation state
- create audit log
- commit

Fulfillment acceptance:
- validate current inventory
- reserve/update inventory
- create/update allocations
- create backorder if needed
- update order state
- audit override/decision where applicable
- commit

Negotiation:
- record request
- apply permitted commercial changes
- recalculate quote
- determine approval
- create new approval instance if required
- update quotation state
- audit
- commit

Billing/payment:
- create/update invoice
- record payment
- update paid amount
- update invoice status
- update billing state
- audit where applicable
- commit

33. FINAL STRUCTURAL PRINCIPLES
======================================================================

1. Modular monolith, not microservices.

2. Routes are thin.
   Business decisions belong in services/engines.

3. Business calculations are backend-authoritative.

4. SQLAlchemy models represent the finalized 30-table schema.

5. Repositories handle persistence/query concerns.

6. Services coordinate business workflows.

7. Engines contain complex reusable business calculations.

8. Customer portal logic is isolated under portal/.

9. Audit logging is centralized and invoked by business operations.

10. Reporting is read/aggregation focused and does not create report tables.

11. Critical workflows should be independently unit-testable without React.

12. Multi-record business operations should use transaction boundaries.

13. Avoid premature abstraction.
    Add files/classes only when complexity justifies them.

14. Do not introduce new tables/modules that conflict with the finalized
    schema or requirements without explicitly identifying the conflict.

15. Every backend module should be traceable to:
    - a requirement/domain area,
    - one or more finalized database entities,
    - and one or more API endpoint groups.

======================================================================
FINAL RECOMMENDATION
======================================================================

Use this structure as the baseline backend skeleton.

The most important separation is:

    ROUTER
       ↓
    SERVICE
       ↓
    ENGINE / BUSINESS RULES
       ↓
    REPOSITORY
       ↓
    SQLALCHEMY MODEL
       ↓
    POSTGRESQL

with:

    CORE = authentication, authorization, DB, config, errors
    AUDIT = cross-cutting audit generation
    REALTIME = optional future capability; not a core dependency

This keeps DealFlow360 simple enough for a 24-hour hackathon while still
matching the finalized modular-monolith architecture and the quotation ->
approval -> fulfillment -> billing -> negotiation -> reporting workflow.
