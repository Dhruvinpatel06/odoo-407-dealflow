DealFlow360 — TECH STACK
=============================

Purpose
-------
This document defines the finalized technology stack for DealFlow360.
It contains technology and architecture decisions only. It does not define
database schema, tables, columns, relationships, or API endpoint specifications.

1. FRONTEND
-----------
- React
- TypeScript
- Vite
- Tailwind CSS
- shadcn/ui
- TanStack Query
- Recharts

2. BACKEND
----------
- Python
- FastAPI
- Pydantic
- SQLAlchemy 2.x
- Alembic

3. DATABASE
-----------
Database Engine:
- PostgreSQL

Database Strategy:
- PostgreSQL is used directly by the backend.
- The application database is self-managed for this project instead of using
  Supabase as the managed PostgreSQL database layer.
- For local development, PostgreSQL should preferably run through Docker.
- FastAPI accesses PostgreSQL through SQLAlchemy 2.x.
- Alembic manages application-database schema migrations.

Important:
- Supabase PostgreSQL is NOT the application database.
- The backend connects to and operates against the project PostgreSQL instance
  directly.
- Authentication is fully owned by the FastAPI application and PostgreSQL session state.

4. AUTHENTICATION
-----------------
Authentication Provider:
- FastAPI-owned manual authentication

Responsibilities:
- FastAPI owns authentication and credential-related flows.
- Passwords are stored as Argon2id hashes.
- FastAPI issues short-lived JWT access tokens.
- Refresh tokens are opaque, high-entropy tokens stored only as hashes in PostgreSQL `auth_sessions`.
- Refresh tokens are rotated and sessions are revocable.
- FastAPI owns application-level authorization and business rules.
- No external authentication provider is used.

5. REALTIME
-----------
Current Decision:
- Supabase Realtime is NOT required as part of the core implementation.

Reason:
- The application's primary PostgreSQL database is now separate from the
  Supabase-managed database.
- Supabase Realtime's database-change functionality is designed around a
  PostgreSQL database connected to the Realtime service.
- Adding a separately self-hosted Realtime service would increase implementation
  complexity and is not necessary for the core hackathon scope.

Future Option:
- Realtime can be added later if required, including self-hosting a compatible
  Realtime service connected to the project PostgreSQL instance.

6. API
------
- REST
- JSON
- FastAPI is the authoritative application/business-logic layer.
- Business rules must not be bypassed by direct frontend-to-database operations.

7. ARCHITECTURE
---------------

Principle:
- One deployable backend application with clear modules separating business
  capabilities.

8. TESTING

13. CHANGE FROM PREVIOUS STACK
------------------------------
Previous database approach:
- Supabase PostgreSQL

Updated database approach:
- Direct/self-managed PostgreSQL

Authentication:
- FastAPI-owned manual authentication remains unchanged.

Realtime:
- Supabase Realtime is no longer a required core dependency because the
  application database is no longer the Supabase-managed PostgreSQL database.

Unchanged:
- React
- TypeScript
- Vite
- Tailwind CSS
- shadcn/ui
- TanStack Query
- Recharts
- Python
- FastAPI
- Pydantic
- SQLAlchemy 2.x
- Alembic
- REST/JSON
- Modular Monolith
- Pytest

Reason for this change:
- PostgreSQL will be implemented and managed directly by the project to satisfy
  the evaluator's recommendation and reduce dependence on Supabase's managed
  database layer, while removing the external authentication dependency and owning authentication inside FastAPI.
