DealFlow360 — FINAL DATABASE SCHEMA SPECIFICATION
=======================================================

DOCUMENT STATUS
---------------
Status: FINALIZED
Purpose: Source-of-truth database schema specification for DealFlow360.
Primary use: Future AI-assisted technical design and implementation, including
SQLAlchemy models, Alembic migrations, API design, backend services, seed data,
tests, and architecture documentation.

SOURCE CONTEXT
--------------
This schema is derived from the finalized DealFlow360 Requirements & Scope
Specification and the confirmed DealFlow360 Technology Stack.

Confirmed database/infrastructure:
- Database: Supabase PostgreSQL
- ORM: SQLAlchemy 2.x
- Migrations: Alembic
- Backend: Python + FastAPI
- Authentication: Supabase Auth
- Architecture: Modular Monolith

The backend is authoritative for business rules. Frontend validation is only
for UX and must not be the sole enforcement mechanism.

----------------

Authentication
-> Customer/Product/Pricing Configuration
-> Quotation Creation
-> Discount Evaluation
-> Blended Risk Evaluation
-> Automatic Approval Routing
-> Fulfillment/Warehouse Allocation
-> Backorder Handling
-> Hybrid Billing
-> Customer Negotiation
-> Negotiation Re-approval
-> Order Confirmation
-> Payment
-> Invoice Status

-> Reporting
-> Audit Trail

GLOBAL DATABASE CONVENTIONS
---------------------------
1. Primary keys:
   - Use UUID primary keys for all application tables.

2. Timestamps:
   - Use TIMESTAMP WITH TIME ZONE for created_at/updated_at and other
     event timestamps.

3. Money:
   - Use NUMERIC(12,2).
   - Do not use floating-point types for monetary values.

4. Percentages:
   - Use NUMERIC(5,2) unless a larger range is explicitly required.

5. Quantities:
   - Use NUMERIC(12,2).

6. Boolean fields:
   - Use BOOLEAN.

7. Status/type values:
   - Prefer PostgreSQL enums for stable finite states such as roles,
     quotation status, approval status, invoice status, etc.

8. JSONB:
   - Use JSONB only where the data is intentionally flexible and a
     dedicated relational table would add unnecessary complexity for the
     hackathon. Current approved use: negotiation requested changes and
     audit value snapshots.

9. All tables should normally contain:
   - id
   - created_at
   - updated_at
   unless a table's lifecycle makes one of these unnecessary.

10. Business calculations must be performed by the FastAPI backend.

TABLE 01: users
----------------
Purpose:
Application-level user identity and authorization metadata. Supabase Auth
owns authentication credentials; this table owns application-specific user
information and role.

Fields:
- id: UUID PK
  Purpose: Internal user identifier.
- auth_user_id: UUID UNIQUE NOT NULL
  Purpose: Identifier of the corresponding Supabase Auth user.
- name: VARCHAR NOT NULL
  Purpose: User display/full name.
- email: VARCHAR UNIQUE NOT NULL
  Purpose: User email address.
- role: ENUM NOT NULL
  Values: SALES_REP, SALES_MANAGER, FINANCE_OPERATIONS, ADMIN, CUSTOMER.
  Purpose: Application authorization role.
- customer_id: UUID FK -> customers.id NULL
  Purpose: Links a customer portal user to the customer/account they belong to.
- is_active: BOOLEAN NOT NULL DEFAULT TRUE
  Purpose: Controls whether the user can access the application.
- created_at: TIMESTAMPTZ NOT NULL
  Purpose: Creation timestamp.
- updated_at: TIMESTAMPTZ NOT NULL
  Purpose: Last modification timestamp.

Constraints:
- auth_user_id UNIQUE
- email UNIQUE
- customer_id is applicable to CUSTOMER users.

TABLE 09: discount_rules
------------------------
Purpose:
Stores configurable discount ceilings based on customer tier and/or
product category.

Fields:
- id: UUID PK
  Purpose: Discount rule identifier.
- customer_tier_id: UUID FK -> customer_tiers.id NULL
  Purpose: Optional tier condition.
- category_id: UUID FK -> product_categories.id NULL
  Purpose: Optional category condition.
- max_discount_percent: NUMERIC(5,2) NOT NULL
  Purpose: Maximum permitted discount percentage for the rule.
- priority: INTEGER NOT NULL DEFAULT 0
  Purpose: Rule precedence when multiple rules are applicable.
- is_active: BOOLEAN NOT NULL DEFAULT TRUE
  Purpose: Whether rule participates in evaluation.
- created_at: TIMESTAMPTZ NOT NULL
- updated_at: TIMESTAMPTZ NOT NULL

Rule interpretation:
- Rules may apply by customer tier, category, or both.
- The discount engine determines the applicable limit.
- For the core tier + category behavior, the stricter applicable limit
  should win.
- The exact rule precedence algorithm is a backend implementation decision,
  but it must support customer-tier and category-specific ceilings.

TABLE 13: quotations
--------------------
Purpose:
Central commercial document and core sales aggregate.

Fields:
- id: UUID PK
  Purpose: Quotation identifier.
- quotation_number: VARCHAR UNIQUE NOT NULL
  Purpose: Human-readable quotation number.
- customer_id: UUID FK -> customers.id NOT NULL
  Purpose: Customer receiving the quotation.

  Purpose: Responsible Sales Representative.

  Values:
    DRAFT
    SENT
    UNDER_NEGOTIATION
    PENDING_APPROVAL
    APPROVED
    REJECTED
    REVISION_REQUIRED
    CONFIRMED
  Purpose: Current quotation lifecycle state.
- subtotal: NUMERIC(12,2) NOT NULL DEFAULT 0
  Purpose: Total before discounts and tax.
- discount_amount: NUMERIC(12,2) NOT NULL DEFAULT 0
  Purpose: Total discount amount.
- order_discount_percent: NUMERIC(5,2) NOT NULL DEFAULT 0
  Purpose: Overall/order-level discount percentage.
- tax_amount: NUMERIC(12,2) NOT NULL DEFAULT 0
  Purpose: Total tax amount.
- total_amount: NUMERIC(12,2) NOT NULL DEFAULT 0
  Purpose: Final quotation amount.
- total_cost: NUMERIC(12,2) NOT NULL DEFAULT 0
  Purpose: Total product/service cost.
- margin_amount: NUMERIC(12,2) NOT NULL DEFAULT 0
  Purpose: Total margin amount.
- margin_percent: NUMERIC(5,2) NOT NULL DEFAULT 0
  Purpose: Total margin percentage.
- risk_score: NUMERIC(8,2) NOT NULL DEFAULT 0
  Purpose: Latest calculated blended discount risk score.
- approval_required: BOOLEAN NOT NULL DEFAULT FALSE
  Purpose: Indicates whether the current quotation requires approval.
- current_approval_level: VARCHAR NULL
  Purpose: Current required approval level, e.g. MANAGER or FINANCE.
- sent_at: TIMESTAMPTZ NULL
  Purpose: Timestamp when quotation was sent to customer.
- last_activity_at: TIMESTAMPTZ NOT NULL
  Purpose: Used to identify stalled quotations.
- valid_until: DATE NULL
  Purpose: Quotation validity/expiry date.
- created_at: TIMESTAMPTZ NOT NULL
- updated_at: TIMESTAMPTZ NOT NULL

Important:
- totals, margin, risk_score, and approval_required are persisted snapshots
  for efficient UI/reporting/workflow access.
- FastAPI must recalculate them whenever relevant quotation data changes.
- quotation lines retain relevant pricing/risk snapshots for auditability.

======================================================================
CRITICAL BUSINESS MODEL DECISIONS
======================================================================

1. QUOTATION IS THE CENTRAL SALES AGGREGATE
-------------------------------------------
Quotation is the primary commercial document.

Primary flow:
customer -> quotation -> quotation_lines -> approval/negotiation
-> order -> fulfillment/billing

2. APPROVAL CONFIGURATION VS EXECUTION
--------------------------------------
approval_policies = reusable configuration.
approval_instances = actual approval workflow executions.
approval_steps = actual reviewer steps.

A quotation may have multiple approval_instances because negotiation can
cause the same quotation to re-enter approval.

3. NO order_lines TABLE
-----------------------
Confirmed order lines are represented by the quotation's confirmed
quotation_lines.

Reason:
Avoid duplicating commercial line data and synchronization problems during
the hackathon.

4. PRICING/RISK SNAPSHOTS
-------------------------
quotation_lines must capture:
- unit_price
- unit_cost
- tax_rate
- allowed_discount_percent
- discount_excess_percent

quotations must capture:
- subtotal
- discount_amount
- tax_amount
- total_amount
- total_cost
- margin_amount
- margin_percent
- risk_score
- approval_required

These values are recalculated by FastAPI whenever relevant data changes.

5. HYBRID BILLING
-----------------
A single order may contain:
- one-time quotation lines
- recurring subscription quotation lines

One-time billing uses invoices with invoice_type=ONE_TIME.
Recurring billing uses subscriptions -> billing_schedules -> invoices.

6. CREDIT NOTES / REFUNDS
-------------------------
No separate refund table is required initially.
Credit notes can be represented by invoices with:
invoice_type = CREDIT_NOTE

Exact refund behavior is governed by subscription-plan configuration and
backend business logic.

7. DEAL HEALTH
--------------
No deal_health table is required.
Deal health is calculated from:
- quotation.last_activity_at
- quotation.risk_score
- fulfillment/order state
- deal_alerts

8. REPORTING
------------
No report/report_definition table is required for the initial schema.
Reporting is implemented through backend SQL queries/aggregations over
transactional tables.

9. CURRENCY
-----------
No currencies table is required.
Currency is represented as a code on price_lists.
Multi-currency beyond required currency-specific price-list behavior is a
bonus scope item.

10. MULTI-COMPANY
-----------------
No company/company hierarchy tables are required.
Multi-company support is explicitly bonus scope.

======================================================================
CORE CONSTRAINTS / INVARIANTS
======================================================================

1. Every quotation must belong to exactly one customer.

2. Every quotation must have exactly one responsible sales representative.

3. Every quotation line must belong to exactly one quotation.

4. Every quotation line must reference exactly one product and may reference
   one variant.

5. Every confirmed order must reference exactly one quotation.

6. One quotation may produce at most one order in the initial implementation.

7. Inventory uniqueness:
   one product + one warehouse = one inventory row.

8. Available stock:
   available_stock = quantity_on_hand - quantity_reserved.

9. Fulfillment allocation quantities must never exceed available inventory
   unless the allocation is explicitly represented as backordered.

10. A quotation with approval_required=true must have an active/pending
    approval workflow before it can be confirmed.

11. Finance approval must not appear when the selected approval policy does
    not require Finance.

12. Approval is sequential:
    when Finance is required, Manager step precedes Finance step.

13. Customer negotiation changes that affect pricing/discount terms must
    trigger recalculation of margin and risk.

14. If negotiated terms require approval, the quotation must create a new
    approval_instance.

15. A quotation may re-enter approval multiple times across its lifecycle.

16. Invoice paid_amount must not logically exceed total_amount unless the
    backend explicitly supports overpayment in a future enhancement.

17. Invoice status must remain consistent with paid_amount.

18. Recurring quotation lines must be capable of producing subscriptions
    and billing schedules.

19. One-time quotation lines must be capable of one-time billing without
    requiring a subscription.

20. Important business actions must create audit_logs records.

SCHEMA DESIGN PRINCIPLE FOR FUTURE AI WORK
======================================================================

When using this document for future technical artifacts:

1. Treat this schema as FINAL unless the user explicitly requests a schema
   change.

2. Do not introduce additional tables merely because they are common in
   CRM/ERP systems.

3. Do not remove any of the 29 finalized tables without explaining which
   requirement becomes harder or impossible to satisfy.

4. Preserve the distinction between:
   - configuration tables
   - transactional tables
   - workflow execution tables
   - audit/alert tables.

5. Preserve quotation_lines as the commercial line source for orders.

6. Preserve approval_instances/approval_steps as separate execution
   records so quotation re-approval is possible.

7. Keep business rules in FastAPI services, not database triggers or React
   code unless a later explicit architectural decision changes this.

8. Use SQLAlchemy 2.x models that map directly to these tables.

9. Use Alembic migrations to create and evolve the PostgreSQL schema.

10. Any future API, backend module, frontend workflow, seed-data plan, or
    test plan must be traceable to these entities and relationships.

11. If a future requirement conflicts with this schema, explicitly identify
    the conflict before changing the schema.

12. Exact formulas that the requirements leave unspecified remain backend
    implementation decisions:
    - blended risk score formula
    - warehouse optimization formula
    - anomaly detection formula
    - delivery slippage formula
    - subscription proration formula
